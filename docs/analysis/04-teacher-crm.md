## Teacher Marketplace / Teacher CRM

**Status: entirely uncommitted/untracked** (all models, controllers, services, migrations, views, and tests for this domain are new working-tree files, not yet on any commit). This is by far the largest single feature area in the working tree — roughly 27 new models, 4 large migrations, 15 controllers under `Teacher/`, 9 services under `Services/Teacher/`, 15 notifications, and 6 dedicated Feature test files (~90 test methods total).

It replaces a much smaller predecessor: the old `App\Http\Controllers\TeacherProfileController` (root namespace, still in HEAD, deleted in working tree) was a ~60-line single-file profile editor over a flat `TeacherProfile` model. It has been superseded by `Teacher\TeacherProfileController` (private CRM side) + `Public\TeacherPublicProfileController` (public listing) backed by a heavily normalized schema.

Any registered user can open a "Basic" teacher account (`POST /teacher/become` → `TeacherAccountController`); the CRM is gated by an `auth + teacher` route-group middleware, not by the legacy `User->role` alone (though `role=teacher/school/admin` still lands users in the CRM per `TeacherAccountTest::test_legacy_teacher_role_lands_in_the_teacher_crm`). Teacher **tier** (`basic` vs `premium`) is a separate axis from student **plan** (`free`/`premium`) — confirmed by `test_student_premium_plan_is_independent_from_teacher_tier`. `TeacherCapabilityService` appears to be the single place that gates premium-only features (payment links, messaging reply, calendar management all require premium tier per tests).

### Profile & Moderation
`TeacherProfile` (extended in-place via `extend_teacher_profiles_for_teacher_crm` migration) carries a full state machine: `draft → submitted_for_review → approved/rejected → suspended → archived`, plus `admin_forced_private` as an orthogonal visibility override. Every transition is journaled to `teacher_profile_moderation_logs` (action, from/to status, admin, notes). Admin side: `Admin/TeacherProfileModerationController` (approve/reject/suspend/reinstate/force-private/add note/update tier/recalculate benefits) + matching Blade views under `admin/teacher-profiles/`. Public side: `/teachers/{slug}` only serves `approved` and non-forced-private profiles (404 otherwise), with owner/admin preview mode adding `noindex`. View counts are deduped per visitor per day via `teacher_profile_views` (ip_hash + date unique constraint), and owner self-views are excluded. A `sitemap.blade.php` + `Public\SitemapController` lists only approved profiles. Profile fields are extensive: bio/headline/methodology, teaching formats/lesson types/genres/age groups/skill levels/languages, SEO title/description, and public contact toggles (`show_email`, `show_phone`).

Related 1:many child resources, each with its own controller/request: `TeacherEducation`, `TeacherInstrument`, `TeacherService` (with premium-gated payment links attached), `TeacherVideo` (YouTube URL validated), `TeacherMedia` (file uploads, public/private visibility, authorized downloads — tested: `test_private_documents_are_not_downloadable_by_other_users`, `test_disallowed_file_types_are_rejected`).

### Booking & Availability (Package 3)
`TeacherBookingSetting` (1:1 per teacher: lesson duration, buffer, advance/notice windows, timezone, `booking_enabled` flag), `TeacherAvailability` (weekly recurring slots), `TeacherAvailabilityException` (date-specific block/extra availability). `TeacherBookingController` exposes public `slots`/`book` endpoints (throttled 10/min); `TeacherCalendarController` (private) handles confirm/reject/cancel/reschedule/complete/no-show state transitions plus a private `teacher_note`. Every transition is journaled to `teacher_appointment_activities`. `MyAppointmentsController` is the student-side mirror (cancel/request-reschedule). Meeting link is `meeting_provider` (`manual` today, comment notes Google Meet as future) + free-text `meeting_url`. Tests cover slot generation, double-booking prevention, availability-boundary rejection, and invalid state-transition blocking.

### Classes, Assignments & AI Homework (Package 2)
`TeacherClass` (+ `teacher_class_students` pivot) groups students. `TeacherStudentInvitation` supports both targeted email invites and multi-use shareable links (`token`), with expiry/revocation, accepted via public `TeacherInvitationAcceptController`.

`TeacherAssignment` is the most structurally interesting piece: it reuses the **existing** `LearningPathQuestionGenerator` rather than inventing a new question engine — `TeacherAssignmentConfigFactory` maps a teacher's UI choice (or free-text AI prompt via `TeacherAiHomeworkService`) to the same `config_json` shape documented in CLAUDE.md for `LearningPathExercise`. Generated questions are frozen into `teacher_assignment_questions` (immutable snapshot, JSON `question_data`) once sent — a comment in the migration explicitly states "student playback and evaluation always read these exact rows," which mirrors the reconstruct-from-session pattern used elsewhere. `TeacherAiHomeworkService` explicitly documents that "the AI never generates question content — it only selects parameters," delegating actual generation to the canonical service — a deliberate, well-reasoned constraint worth preserving.

Delivery: `teacher_assignment_recipients` (per-student status/best_score/attempts_count) and `teacher_assignment_attempts` (per-attempt answers/score/duration), with `max_attempts` enforcement and locking of questions after `send`. `TeacherStudentReward` (stickers/badges/labels/milestones) can be attached to assignment completion. Tests confirm interval-direction non-regression and that the config factory produces generatable configs "for all types" — i.e., all 10 practice types are assignable.

### Student Relationship Tools
`TeacherStudentRelationship` is a mutual-consent state machine (`pending_teacher_request | pending_student_approval | active | declined | revoked_by_teacher | revoked_by_student | archived`) — either party can initiate, the other approves; `MyTeachersController` is the student-side approve/decline/destroy surface. Almost every other teacher↔student feature (notes, tags, rewards, classes, messaging, assignments) is gated on an **active** relationship — heavily tested (`test_notes_tags_rewards_require_active_relationship`, `test_messaging_requires_active_relationship`, `test_revoked_relationship_blocks_new_messages`). `TeacherStudentNote` (private notes), `TeacherStudentTag` (+ assignment pivot, teacher-scoped custom tags).

### Messaging
`TeacherConversation` (unique teacher+student pair) / `TeacherConversationMessage` (soft-deletable, read_at) / `TeacherConversationAttachment` (private, authorized download only). Dual controllers for the two sides: `Teacher\TeacherMessageController` and `StudentTeacherMessageController`. Basic-tier teachers can read but not reply (`test_basic_teacher_can_read_but_not_reply`) — another premium gate via `TeacherCapabilityService`.

### Reviews
`TeacherReview` — one review per student per teacher profile (unique constraint, upserted not duplicated), 1–5 rating, `approved | hidden | pending` status, with a report flow (`reported_at`/`report_reason`) reviewable by admins via `Admin/TeacherReviewModerationController`. Only reviewable by students with a relationship to the teacher (implied "connected student" language in tests) — public profile only shows approved reviews.

### Subscription Benefits (Premium Incentive Engine)
`TeacherSubscriptionBenefitService` is a well-documented incentive engine: teachers with ≥N active/approved Premium students (both thresholds admin-configurable via `SystemSetting`) automatically earn a discount, and above a higher threshold a free period, with "highest benefit wins, only one active at a time" semantics, a grace period on losing eligibility, full idempotent recalculation, and an audit trail in `teacher_subscription_benefit_histories`. **Explicitly documented in the code as not wired to real billing yet**: *"Harmoniva does not process payments in Phase 1, so benefits are recorded and surfaced to admins/teachers; billing integration consumes them later."*

### Risks & Observations
- **Payment links are not a payment system.** `TeacherPaymentLink` is just an admin-curated external URL (`url:https` validated) with a label/price-text/visibility (public / approved-students-only / appointment-confirmation) — Harmoniva does not process any money itself for lessons. Same "Phase 1, no billing" caveat applies to the subscription-benefit engine above. Anyone reviewing this domain for PCI/payments risk can stand down — there is none in-repo; the risk is purely the accuracy of the "no billing yet" assumption holding as this ships.
- **Scope size vs. commit state**: this is ~90 tests across 6 files and appears functionally complete and well-tested (moderation, booking edge cases, relationship-gating, attempt-limits, review upsert-not-duplicate are all explicitly covered), but **zero of it is committed**. A `git status` shows it entirely as untracked/modified working-tree state on `main`. Before any deploy or handoff, this needs a commit (or several logically-scoped ones) — a crash or `git clean`/`reset` right now would destroy the entire teacher marketplace feature.
- **Legacy role coupling**: `role=teacher`/`role=school` (pre-existing `User->role` enum from CLAUDE.md) still grants CRM access alongside the new `teacher` account flag — two overlapping "is this a teacher" signals (`User->role` and presumably a boolean/flag checked by the `teacher` middleware) now coexist. Worth confirming the `teacher` middleware's exact check (not read in this pass) to ensure no gap where a `role=school` user gets CRM access without ever going through `TeacherAccountController::store` (i.e., without a `TeacherProfile` row at all) — `TeacherProfileEditorTest::test_role_based_user_without_profile_gets_draft_created_on_profile_edit` suggests this is handled by lazily creating a draft profile, which is reasonable but worth knowing about.
- **`teacher_subscription_benefit_id` foreign key** uses an explicit short index name (`tsbh_benefit_id_foreign`) with a code comment noting Laravel's default generated name exceeds MySQL's 64-char identifier limit — same pattern repeated for several other FKs in the package 2/3 migrations (`ta_questions_assignment_fk`, `ta_recipients_assignment_fk`, etc.). This is a good, deliberate pattern; if adding further teacher-domain migrations, keep following it or MySQL migration failures will result.
- **No payment/webhook integration found in this domain** — contrast with the Email Center domain (SES) and note there is currently no Stripe/payment-gateway code anywhere in `app/Services/Teacher` or the teacher migrations; any future "Phase 2 billing" work is a clean slate here.
- `CheckUserRestriction` middleware (new, untracked) globally blocks restricted users to `/`, `/dashboard`, `/logout`, `/language/switch` only — this interacts with the teacher CRM (a restricted teacher loses all CRM access) and is a cross-cutting concern worth flagging to whichever domain owns global auth/moderation in the final report.
