## Email Center & Support Inbox

Status: mostly **untracked/uncommitted** in git (this is freshly built, not yet merged to `main`). CLAUDE.md's summary of this system is accurate at a high level; this section adds implementation detail and a code-level verification.

### Architecture

**Entry point:** `App\Services\EmailCenter\EmailDispatchService::dispatch()` (`app/Services/EmailCenter/EmailDispatchService.php`) is the single place that creates an `EmailMessage` row and queues `App\Jobs\SendEmailCenterMessage`. It branches on whether `$emailType` is in `EmailMessage::MARKETING_TYPES`:
- Marketing → blocked if `SuppressionService::canReceiveMarketing()` fails (unverified, suspended, suppressed, or over the rolling-7-day frequency cap).
- Transactional → only blocked by a hard-bounce suppression entry (`isHardSuppressed()`).

**Sending:** `SendEmailCenterMessage` (`app/Jobs/SendEmailCenterMessage.php`) is rate-limited via Laravel's `RateLimited('email-center-send')` queue middleware, re-checks suppression at send time (handles the race between queueing and sending), renders through `TemplateRenderer`, sends via `Mail::mailer('ses')`, captures the `X-SES-Message-ID` response header, and writes a synthetic `EmailEvent` (`event_type: sent`, `source: internal`) in addition to whatever SES later reports. Retries 3x with `[60, 300]`s backoff; on final failure marks the message `failed` and increments the campaign's `failed_count`. Has a `failed()` handler as a second safety net if the queue itself gives up.

**Campaigns:** `App\Jobs\ProcessEmailCampaign` (`app/Jobs/ProcessEmailCampaign.php`) resolves `SegmentBuilder::query()`, excludes users already queued for that campaign (`whereNotIn(... campaign->messages())`), and dispatches one `SendEmailCenterMessage`-triggering call per user in chunks of 200 via `chunkById`. `App\Console\Commands\ProcessEmailCampaigns` (scheduled every minute, `routes/console.php:20`) starts due `scheduled` campaigns and flips `sending` → `sent` once no `queued` messages remain (2-minute grace period after start).

**Automations:** `AutomationEngine::run()` (`app/Services/EmailCenter/AutomationEngine.php`) iterates the 6 enabled automations (`welcome`, `first_exercise_reminder`, `learning_path_reminder`, `weekly_progress`, `re_engagement`, `premium_upsell`), builds a due-users query per key with per-automation cooldown/never-received guards, and caps each run at 200 sends (`$batchLimit`) so a newly-enabled automation can't flood the queue. Runs every 15 minutes (`routes/console.php:23`).

**Template rendering:** `TemplateRenderer` (`app/Services/EmailCenter/TemplateRenderer.php`) does `{{var}}` substitution, rewrites every external `href` into a signed click-redirect (`email.click`, skips unsubscribe links), appends UTM params only to links back to the app's own host, injects a 1×1 open-tracking pixel before `</body>`, and appends an unsubscribe footer for marketing mail if the template didn't already include one. Has a separate `preview()` path with sample data for the admin UI (no tracking injected).

**Inbound SES events:** `Webhooks\SesWebhookController::events()` (`app/Http/Controllers/Webhooks/SesWebhookController.php`) validates the SNS envelope via `SnsMessageValidator`, then does a **second** replay guard on top of per-event dedup — `Cache::add('sns-mid-{MessageId}', ..., 6h)` — before auto-confirming `SubscriptionConfirmation` via an outbound GET to `SubscribeURL`, or handing `Notification` payloads to `SesEventProcessor::process()`.

`SnsMessageValidator` (`app/Services/EmailCenter/SnsMessageValidator.php`) implements the full official SNS verification algorithm: required-field check, topic ARN allow-list (`config('email-center.allowed_topic_arns')`, sourced from `SES_EVENT_TOPIC_ARN`/`SES_SUPPORT_TOPIC_ARN` env vars), timestamp window (`-1 day` to `+15 min`), signing-cert URL host/path validation (`^sns\.[a-z0-9\-]+\.amazonaws\.com$`, must end `.pem`), fetches+caches the cert for 1 day, and does `openssl_verify` (SHA1 or SHA256 depending on `SignatureVersion`). This is a real security control, not a stub.

`SesEventProcessor::process()` (`app/Services/EmailCenter/SesEventProcessor.php`) maps SES event names to internal types, computes a `dedup_hash` (sha256 of type/messageId/detail/timestamp) and short-circuits if that hash already exists in `email_events`, matches the target `EmailMessage` by `ses_message_id` first and falls back to a `tracking_token` mail tag, applies monotonic status upgrades via a `STATUS_RANK` map (status never regresses, e.g. `opened` won't be overwritten back to `delivered`), increments campaign counters exactly once per lifecycle stage (guarded by `!$message->delivered_at` etc.), and auto-suppresses on **permanent** bounces and all complaints (soft bounces are recorded as events only, surfaced to admins for manual action per CLAUDE.md).

**Suppression / frequency cap:** `SuppressionService` (`app/Services/EmailCenter/SuppressionService.php`) — `isSuppressed`, `suppress` (upsert by email), `unsuppress`, `isOverFrequencyCap` (reads `SystemSetting::get('email_frequency_cap', ...)` with a config fallback; `0` = unlimited), `canReceiveMarketing` (verified + not suspended + not suppressed + under cap).

**Tracking endpoints** (`app/Http/Controllers/EmailTrackingController.php`, public routes in `routes/web.php:556-568`):
- `GET /email/open/{token}` — unsigned (must work as a bare `<img src>`), returns a static 1×1 GIF regardless of match, records an internal `opened` event and bumps `opened_at`/campaign counter idempotently.
- `GET /email/click/{token}?url=` — **signed** route; rejects any `url` not starting `http(s)://`, records `clicked` (and backfills `opened_at` if missing), then `redirect()->away($target)`. Because the route requires a valid Laravel signature over the full query string (including `url`), an attacker cannot tamper with the redirect target without invalidating the signature — this is not an open-redirect despite superficially looking like one.
- `GET/POST /email/unsubscribe/{token}` — signed; POST variant serves both the confirm-button flow and RFC 8058 one-click `List-Unsubscribe-Post` from mail clients, both call `SuppressionService::suppress(..., 'unsubscribe', 'user')`.
- All three routes are CSRF-exempt (confirmed via `bootstrap/app.php` per CLAUDE.md) — required since they're hit by mail clients/pixel loaders with no session.

**Support inbox:** `SupportMailFetcher` (`app/Services/EmailCenter/SupportMailFetcher.php`, driven by `App\Console\Commands\FetchSupportMail`, scheduled every 5 min) polls IMAP and threads by Message-ID/References into `support_conversations`/`support_messages`. Config toggle `support_inbound_mode` (`imap` / `external` / `disabled`) in `config/email-center.php` lets ops fall back to an external webmail link (`webmail_url`) without code changes. Outbound admin replies go through `SupportReplyMail` (`app/Mail/SupportReplyMail.php`) via the `ses` mailer with `In-Reply-To`/`References` headers (per CLAUDE.md; not independently re-verified line-by-line here).

**Admin surface:** `Admin\EmailCenterController`, `EmailCampaignController`, `EmailAutomationController`, `EmailTemplateController`, `SupportInboxController` (all `app/Http/Controllers/Admin/`) plus views under `resources/views/admin/email-center/`. `EmailCenterSeeder` (`database/seeders/EmailCenterSeeder.php`) seeds the 6 automations, all **disabled** by default (confirmed consistent with CLAUDE.md).

### Test coverage (`tests/Feature/EmailCenterTest.php`, 401 lines, 18 tests)

Covers: dispatch happy path, marketing-blocked-when-suppressed, transactional-allowed-despite-unsubscribe-but-not-hard-bounce, frequency cap, unverified-users-never-get-marketing, open pixel, click-redirect-requires-valid-signature, unsubscribe flow, webhook rejects invalid payload, webhook processes a delivery event, hard bounce → suppression, complaint → suppression, **SES event idempotency** (duplicate events), segment builder filters/exclusions, campaign send flow queues per-segment, welcome automation sends-once, admin pages load, non-admin access denied. This is unusually thorough test coverage for a feature this size — the idempotency and signature-validation paths (the two things most likely to cause silent data corruption or a security hole) are both explicitly tested.

### Risks & Observations

1. **IMAP cert validation disabled by default** — `config/email-center.php:45`, `support_imap.validate_cert` defaults to `false`. Low risk in practice since the default host is `127.0.0.1` (local Dovecot), but if `SUPPORT_IMAP_HOST` is ever pointed at a remote host this becomes a silent MITM risk with no code change required to reintroduce it safely (i.e. there's no prod/local distinction enforced in code).
2. **Outbound HTTP calls inside the webhook request path** — `SesWebhookController::events()` does a synchronous `Http::timeout(10)->get($payload['SubscribeURL'])` for `SubscriptionConfirmation`, and `SnsMessageValidator::verifySignature()` does a synchronous (cached 1 day) fetch of the signing cert. Both are timeout-bounded and the cert fetch is cached, so this is a minor latency/availability coupling rather than a real bug — but a webhook endpoint blocking on an outbound call to AWS is worth knowing about if SES-side retry/backpressure behavior ever becomes relevant.
3. **No apparent rate limiting on the public webhook route itself** (`routes/web.php:558`) beyond the SNS signature check + the 6-hour dedup cache — a flood of *validly signed* SNS traffic (unlikely but not impossible if the topic ARN allow-list were ever misconfigured) would still hit `SesEventProcessor` unthrottled. Low priority given the allow-list gate.
4. **Good practice, worth flagging as such**: status transitions are monotonic (`STATUS_RANK`), all counter increments are idempotency-guarded on the timestamp field (`!$message->delivered_at` etc.) rather than blindly incrementing, and every event (internal + SES) funnels through a `dedup_hash` unique check — this is a well-engineered idempotent event pipeline, not a naive webhook handler.
5. **Click-tracking "open redirect" is not exploitable** as noted above — worth documenting explicitly so a future security review doesn't waste time re-deriving that the signed-route requirement neutralizes it.
6. The `email:process-campaigns` "finalize" check (`ProcessEmailCampaigns.php:25-32`) treats a campaign as complete once no `queued` messages remain, but doesn't check for `failed`/`suppressed` terminal states explicitly — that's fine (those are also non-`queued`), just note the completion signal is purely "nothing left in `queued`," so a campaign that fails 100% of sends still reports as `sent`/`completed_at` rather than a distinct failure state at the campaign level (per-message `failed_count` is tracked, but there's no campaign-level "some/all sends failed" status).
