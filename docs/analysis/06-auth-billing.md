## Auth, Users, Roles, Plans & Billing

### User model (`app/Models/User.php`)
- Single-table `User` model covers four roles (`user`, `teacher`, `school`, `admin`) and two plans (`free`, `premium`), plus an orthogonal "teacher account" concept: **any** user (including students/admins) can additionally hold a `TeacherProfile` and act as a teacher (`hasTeacherAccount()`), independent of `role`. `homeRoute()` sends teacher-account holders straight to `teacher.dashboard`.
- Role/plan helpers: `isAdmin()/isUser()/isTeacher()/isSchool()`, `isPremium()/isFree()`, `isSuspended()` (via `suspended_at` timestamp), `isRestricted()` (via `is_restricted` bool).
- Entitlements: `canAccess(string $feature)` reads `config('plans.{role}.{plan}.{feature}')` (admin bypasses everything); `getPlanLimit(string $feature)` prefers a DB-driven `Plan` row (cached 300s, keyed `role.type`) over the `config/plans.php` fallback — so admins can override limits at runtime via the `plans` table without a deploy.
- Huge relationship surface: practice/exercise history, `UserProfile`, `Subscription`/`Invoice`, Teacher-CRM relations (`studentRelationships`, `teacherAssignments`, `teacherClasses`, `teacherSubscriptionBenefits`, etc.), and social graph (`following`/`followers` many-to-many via `follows` pivot, `feedItems`). `booted()` hooks `FeedItem::recordNewMember()` on every user creation.
- Activity logging (`spatie/laravel-activitylog`) only logs `name/email/role/plan` changes, dirty-only, under log name `admin` — i.e. role/plan escalations are audited but profile edits are not.
- `$fillable` includes `role`, `plan`, `is_restricted`, `suspended_at` directly — a mass-assignment risk in principle, but every `User::create()`/`update()` call found (registration, Google OAuth, admin controllers) passes an explicit field array rather than `$request->all()`, so this is contained today but is a landmine for future code.

### Registration & Auth (`app/Http/Controllers/Auth/*`, `routes/auth.php`)
- Standard Laravel Breeze controller set (`RegisteredUserController`, `AuthenticatedSessionController`, password reset/confirm, email verification) plus a custom `SocialAuthController` for Google.
- `RegisteredUserController::store()` validates `role` as `in:user,teacher,school` — **admin cannot be self-registered**, good. New users always start on `plan => free`. Locale is captured from session, and a hardcoded `locale → country` map seeds a `detected_country` session value.
- `SocialAuthController` (Google via `laravel/socialite`, driver configured presumably in `config/services.php`): matches existing user by `google_id`, then falls back to matching by `email` (auto-links Google to an existing password account and backfills `google_id`/`avatar_url`), else creates a new `role => user, plan => free` account with `email_verified_at` pre-set. Error message on OAuth failure is hardcoded Turkish ("Google ile giriş yapılamadı...") despite the app having a 15-locale i18n system — inconsistent with `resources/lang`.
- `routes/auth.php` (64 lines) is the standard Breeze route set: register, login, forgot/reset password, email verify, confirm password, logout, plus presumably the two Google routes (`auth/google`, `auth/google/callback`).

### Middleware (`app/Http/Middleware/*`, registered in `bootstrap/app.php`)
Aliases: `admin`, `teacher`, `school`, `plan`, `track.exercise`, `check.restriction`. Global web-group middleware (applied to every request): `SetLocale`, `NoIndex`, `CheckUserRestriction`.
- `AdminMiddleware` / `SchoolMiddleware`: simple `role !== 'x'` → `abort(403)` checks.
- `TeacherMiddleware`: grants access if `role` is legacy `teacher|school|admin` **or** `hasTeacherAccount()` — reflecting the newer "any user can run a teacher account" model.
- `CheckPlanFeature` (`plan:{feature}` route middleware): admin bypass, then `$user->canAccess($feature)`; returns JSON 403 for XHR or redirects to dashboard with a hardcoded Turkish flash message ("Bu özellik Premium plan gerektirir...") — same i18n inconsistency as above.
- `CheckUserRestriction` (new, untracked, applied globally): if `is_restricted` and not admin, blocks all routes except an allowlist (`/`, `/dashboard`, `/logout`, `/language/switch`), redirecting elsewhere with another hardcoded Turkish message. This is the enforcement point behind the "restricted/suspended users excluded from email suppression list" behavior noted in `CLAUDE.md`'s Email Center section.
- CSRF is explicitly exempted for `webhooks/aws/ses/*` and `email/unsubscribe/*` (SNS + RFC 8058 one-click unsubscribe), consistent with Email Center design.

### Policies (`app/Policies/`) — brand new, one file
- `TeacherProfilePolicy` is the **only** policy in the codebase currently: `view`/`update` restricted to profile owner (or admin for view), `submit` additionally requires `TeacherProfile::canBeSubmitted()`, `managePaymentLinks` gated by `TeacherCapabilityService::canUseExternalPaymentLinks()` (a premium-teacher capability), `moderate` admin-only. Everything else in the app (all Admin controllers, practice/exercise access) is authorized via middleware/manual role checks rather than Laravel Policies — this is the first policy-based authorization introduced, scoped only to the new Teacher CRM feature.

### Plans & entitlements (`config/plans.php`)
Three role trees (`user`, `teacher`, `school`) × two tiers (`free`, `premium`), each a flat feature-flag/limit map:
- `user`: `daily_exercises_per_type` (3 free / -1 premium), `ai_exercises`, `ai_coach` (`limited`/`full`), `detailed_charts`, `all_modules`, `saved_plans_limit` (3/-1), `adaptive_difficulty`, plus games limits (`games_daily_plays_per_type`, `games_daily_plays_total`, `games_leaderboard`).
- `teacher`: `max_students` (5/-1), `crm` (false/true — free teachers don't get CRM), `content_publishing`, `calendar`, `detailed_reports`.
- `school`: `max_teachers` (3/-1), `max_students` (20/-1), `advanced_reports`.
- `-1` is the universal "unlimited" sentinel, consumed by `canAccess()`/`getPlanLimit()`/`DailyExerciseCount::getRemainingForUser()`.
- **Note**: DB-backed `Plan` rows (via `Plan::where('is_active', true)`, cached 5 min) take precedence over this file when a matching `role.type` plan exists — so this config is really just the seed/fallback, and the admin-managed `plans` table (edited via `Admin/PlanController`) is the live source of truth in production.

### Daily free-tier limiting (`app/Models/DailyExerciseCount.php`)
Simple per-user/per-practice/per-day counter row. `incrementCount()` does `firstOrCreate` + `increment` (one row per user/practice/date). `getRemainingForUser($userId, $practiceId, $limit)` returns `PHP_INT_MAX` for `-1` limits, else `max(0, limit - used)`. Enforcement is presumably wired through the `track.exercise` (`TrackExerciseUsage`) middleware alias, not reviewed in depth here (out of scope — practice engine is another domain).

### Billing / Subscriptions (`app/Models/{Plan,Subscription,Invoice,Coupon}.php`)
- **No payment gateway is integrated.** `composer.json` has no Stripe/Paddle/PayPal/Braintree package. `Subscription` has `payment_provider` and `external_id` columns clearly intended for a future gateway hook, but nothing populates them today.
- `Admin/SubscriptionController` is plain CRUD (`index/show/edit/update/destroy`) over the `subscriptions` table — no `store`/checkout action was found, meaning subscriptions are **manually created/edited by admins**, not self-service checkout by users. This is effectively an internal billing ledger + entitlement override system, not a production payment flow.
- `Invoice::generateNumber()` builds sequential `INV-YYYYMM-NNNN` numbers by string-parsing the last invoice's suffix — fine at low volume, but not concurrency-safe (a race between two invoice creations in the same request cycle could produce a duplicate number; no DB-level uniqueness enforcement was checked here).
- `Coupon` has full discount-code semantics (`type`/`value`, `max_uses`/`used_count`, `applicable_plans`/`applicable_roles` as JSON arrays, `starts_at`/`expires_at`) with an `isValid()` helper — but with no payment gateway, it's unclear what actually *redeems* a coupon (likely wired into the admin-manual subscription flow; not traced further, out of scope for this fork).

### Risks & Observations
1. **Billing is administrative, not transactional.** There is no Stripe/PSP integration, no checkout route, no webhook handler for payment events. All `premium` upgrades appear to be granted manually by an admin editing a `Subscription`/`User.plan` row. If the product intends self-serve payment, this is a major gap, not a polish item.
2. **Mass-assignable `role`/`is_restricted`/`suspended_at` on `User::$fillable`** is currently safe only because every write site uses explicit arrays — there's no model-level guard (no `$guarded`, no custom `fill()` override). One future `User::create($request->validated())` or `->fill($request->all())` call would be a privilege-escalation bug (self-serve admin/restriction-bypass). Worth a code-review note/guard rather than an incident today.
3. **Hardcoded Turkish user-facing strings** in `CheckUserRestriction`, `CheckPlanFeature`, and `SocialAuthController` bypass the app's `__()`/15-locale i18n system entirely — English or other-locale users hitting these paths see Turkish error text. Straightforward but currently-unfixed inconsistency.
4. **Authorization is still mostly middleware/role-string based**, not Policy-based — `TeacherProfilePolicy` is a green shoot but the rest of the app (all Admin controllers) relies on the blunt `AdminMiddleware` role check with no per-resource policy layer. Not wrong for an admin-only area, but means finer-grained admin permissions (e.g., a "support-only" admin) aren't structurally possible yet.
5. **`is_restricted` vs `suspended_at`** are two separate, seemingly overlapping moderation states (`isRestricted()` blocks nearly the whole site via middleware; `isSuspended()` exists as a helper but no middleware enforcement of it was found in this pass) — worth clarifying the intended distinction (e.g., suspension = pending review vs. restriction = active penalty) since two similar-but-different flags increase the chance of inconsistent enforcement.
6. **DB-first plan limits** (`Plan` table overriding `config/plans.php`) is a nice piece of design — lets admins tune entitlements live — but means reading `config/plans.php` alone (as CLAUDE.md currently documents) can be misleading in production if the `plans` table has been edited; worth cross-checking `Admin/PlanController` when debugging entitlement issues.
